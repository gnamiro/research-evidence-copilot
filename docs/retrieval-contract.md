# Retrieval contract

## Purpose

This contract defines how a user query is converted into an embedding and used
to retrieve evidence chunks from PostgreSQL.

Retrieval returns source evidence only. It does not generate, summarize, or
rewrite an answer.

## Input

The retrieval workflow accepts:

- `query`: the user’s natural-language search query.
- `top_k`: maximum number of evidence chunks to return.

Validation rules:

- `query` must be a string.
- `query` must not be empty or whitespace-only.
- Leading and trailing whitespace is removed before encoding.
- `top_k` must be an integer greater than zero.
- Boolean values are not valid integers for `top_k`.
- The default `top_k` is `5`.

The original query must not be stored in or added to retrieval results.

## Query embedding

The query must be encoded with the same embedding configuration used for
document chunks:

- Model: `sentence-transformers/all-MiniLM-L6-v2`
- Model revision: `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`
- Encoding method: `encode_query`
- Embedding dimension: `384`
- Normalize embedding: `true`

The resulting query embedding must:

- contain exactly 384 values;
- contain only finite values; and
- have a magnitude approximately equal to 1.

## Eligible document embeddings

A document embedding is eligible only when:

- its `model_name` exactly matches the query model;
- its `model_revision` exactly matches the query model revision; and
- it contains a valid 384-dimensional vector.

Embeddings generated by another model or revision must not appear in the
results.

## Similarity calculation

Retrieval uses pgvector cosine distance.

Cosine distance is calculated with the pgvector `<=>` operator.

The user-facing similarity score is:

similarity_score = 1 - cosine_distance

Cosine similarity may range from `-1` to `1`. A larger score means the chunk is
more similar to the query.

## Ranking

Results must be ordered by:

1. cosine distance ascending; and
2. `chunk_id` ascending when two results have equal distance.

The `chunk_id` tie-breaker makes repeated searches deterministic.

The workflow returns at most `top_k` results. It may return fewer results when
fewer eligible embeddings exist.

When no eligible evidence exists, retrieval returns an empty list.

## Result fields

Each result represents one evidence chunk and contains:

| Field | Type | Null? | Meaning |
|---|---|---:|---|
| `chunk_id` | text | No | Deterministic identifier of the evidence chunk. |
| `arxiv_id` | text | No | arXiv paper identifier. |
| `version` | integer | No | Paper version from which the evidence was created. |
| `evidence_type` | text | No | Type of evidence, initially `abstract`. |
| `chunk_index` | integer | No | One-based chunk position within the evidence source. |
| `text` | text | No | Exact stored evidence text. |
| `section` | text | No | Source section, initially `abstract`. |
| `source_url` | text | No | Link to the original arXiv source. |
| `similarity_score` | float | No | Cosine similarity between the query and chunk. |

## Evidence and citation behavior

Retrieval results must preserve the exact stored chunk text and source
metadata.

The retrieval layer must not:

- summarize the chunk;
- paraphrase its text;
- replace its source URL;
- invent missing citation metadata; or
- include the user query in the result record.

These fields provide the evidence boundary required by later grounded answer
generation.

## Errors and empty results

Invalid inputs raise an error before a database search is performed.

A valid query with no matching evidence is not an error. It returns an empty
list.

## Initial scope

This checkpoint uses exact cosine search.

The following are outside the initial retrieval scope:

- HNSW or IVFFlat indexes;
- keyword or hybrid search;
- reranking;
- similarity thresholds;
- answer generation;
- Ollama calls; and
- citation validation.
